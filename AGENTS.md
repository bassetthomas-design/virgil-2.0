# Règles pour les agents de code

Ces règles s’appliquent à tout le dépôt. Les règles d’architecture cible s’appliquent au code nouveau ou modifié ; ne pas refactorer du code legacy sans rapport en dehors de la tâche de sa phase. Lire [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), source de vérité sur l’existant et la cible, puis [docs/ROADMAP.md](docs/ROADMAP.md) et [docs/PROJECT_STATUS.md](docs/PROJECT_STATUS.md) avant de travailler.

- Une PR par tâche, avec un périmètre explicite, les vérifications réalisées et les limites connues. Ne pas mélanger une tâche de documentation avec un refactor C#.
- Jamais de `new XxxService()` dans les vues ou ViewModels : tous les services passent par DI. Utiliser Microsoft.Extensions.Hosting pour la composition et CommunityToolkit.Mvvm pour les ViewModels ; garder les vues minces.
- Tout accès OS de l’application passe par Virgil.Infrastructure : fichiers, registre, processus, réseau et élévation. Core contient la logique métier et les politiques de sécurité, sans appel OS direct. Centraliser les lancements via un seul IProcessRunner. Le helper reste un exécutable privilégié distinct, limité à son allowlist et ne référençant que Contracts parmi les projets Virgil.
- Toute action destructive exige un ConfirmedPlan et un test de sécurité. Seul ConfirmationService crée le plan après consentement explicite ; le plan est lié au hash de l’aperçu et expire. L’exécution refuse un plan absent, expiré ou non conforme avant tout effet OS. Tester le refus et l’absence d’effets. Un booléen `userConfirmed` ne constitue pas le contrat cible.
- Ne jamais affaiblir les gardes existants : CleanupPathGuard, CleanupSafetyClassifier, ProcessProtectionPolicy et l’allowlist de l’ElevatedHelper. Les conserver ou les renforcer, avec leurs tests, pendant la migration ; ne pas supprimer une protection sous prétexte que son remplacement est documenté.
- Respecter les filets de sécurité : nettoyage vers quarantaine/corbeille et sauvegarde vérifiée avant modification du démarrage ; un échec de ces protections bloque l’action. Créer et vérifier un point de restauration uniquement avant les changements système : pilotes, réparations Windows via le helper, modifications du démarrage, du registre ou des services. Il n’est pas requis pour le nettoyage, protégé par quarantaine/corbeille, ni pour les actions sur les processus. Si la restauration système est désactivée ou limitée, expliquer la situation et proposer de l’activer ; ne permettre de continuer sans cette protection que via une confirmation de niveau Critique indiquant explicitement « aucun point de restauration ». Ne jamais ignorer cette situation en silence. Hors de cette dérogation explicite, un échec de création ou de vérification bloque le changement système.
- Tous les textes UI sont en français : libellés, confirmations, erreurs et messages `[VIRGIL]`. Le chat et le tray proposent des actions et passent par ConfirmationService ; ils n’agissent jamais seuls.
- La CI GitHub Actions sur Windows (`.github/workflows/build.yml`) est la seule référence de build. Ne pas déclarer un build validé sur la base d’une compilation locale ou Linux ; fournir le résultat Windows, ou indiquer qu’il est en attente/en échec. Aucun environnement de développement local ne doit être requis de l’utilisateur final.
- Distinguer systématiquement l’existant de la cible. Mettre à jour la documentation quand un changement architectural est réellement livré. La phase 0 est un refactor sans nouvelle fonctionnalité ; le lot 0a est limité au nettoyage et aux documents, sans modification C#.

- Ne jamais ajouter de workflow qui commit/push, de payload base64, ni de force-push. Ne pas modifier `.github/workflows` sauf si la tâche le demande explicitement.
- Les tests qui nécessitent Windows (chemins Windows, registre, ACL, WMI) doivent porter `[Trait("Category","Windows")]`. Les exécutions Linux/Codex peuvent les filtrer avec `dotnet test --filter Category!=Windows` ; la CI Windows reste la référence.
